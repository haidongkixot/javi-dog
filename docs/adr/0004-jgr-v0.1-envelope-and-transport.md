# ADR-0004: JGR v0.1 — own minimal envelope over HTTPS batches, OTLP accepted at the edge

- Status: Accepted by the implementer; **owner review pending** (draft protocol; revisit at v0.2)
- Date: 2026-10-20
- Deciders: Project owner (Hai), Claude (implementer)
- Modules: JD-M01, JD-M02, JD-M05, JD-C01…C03

## Context and problem statement

Javi's Dog needs one contract for signals from many coding tools. The owner's priorities: speed, stability and optional encryption of signals, with privacy by default (brand UX principle 3). Some tools already export OpenTelemetry (OTLP); others only offer hooks or nothing (GitHub fallback).

## Considered options

1. **Adopt OTLP as the only protocol** — tools that speak OTLP connect directly.
2. **Adopt CloudEvents 1.0 as the envelope** with JGR-specific `data`.
3. **Own minimal envelope (JGR)** with CloudEvents-like identity fields, plus an OTLP receiver at the edge that normalizes into JGR.

## Decision outcome

Chosen: **option 3**.

- OTLP is excellent for tools that already emit it, but it is heavy for a 20-line hook script, carries no notion of privacy class, and its semantics (spans/metrics/logs) do not map 1:1 to "thread status" and "attention requested". So the gateway will *accept* OTLP/HTTP from Claude Code, Codex and Gemini CLI and translate it (S3/S5), while JGR stays the internal and hook-level contract.
- CloudEvents gives identity and type conventions but no usage, status or privacy semantics; adopting its full envelope adds fields without adding guarantees. JGR keeps CloudEvents' spirit (`event_id`, producer, type, time) in a smaller shape and can be wrapped in a CloudEvent later if interoperability demands it.
- Privacy classes are validated **at the envelope** and violations are rejected (not stripped), making privacy testable via shared conformance vectors.
- Deltas + `event_id` dedupe + per-thread `sequence` give at-least-once delivery without inflated counters and with visible gaps.

### Consequences

- Good: a tiny, testable contract; one validator shared by SDK, collectors and gateway; privacy enforced by construction.
- Good: tools with native OTLP need no custom code from users.
- Bad: two inbound paths (JGR + OTLP) to maintain; the OTLP translation must be covered by its own conformance tests.
- Bad: v0.1 has bearer-token auth only; request signing (HMAC) and per-project hashing salts come in v0.2 / S5.

## Changes

- 2026-10-20 (G1 review): refs tightened to opaque identifiers `^[A-Za-z0-9_:-]+$` — a breaking change to the draft, made because paths and emails were accepted as `thread_ref` / `agent_ref` (reproduced by probe). Versioning text (§11) aligned with JGR-R11.
